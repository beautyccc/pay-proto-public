## 5. 影响四项

| 项 | 影响 |
|---|---|
| 包体积 | 这是 HTML 原型仓库，不是小程序包：`mobile.js` +36.5 KB、`style.css` +4.7 KB、`index.html` −1.5 KB。若迁移到小程序，二维码编码器可抽为 `utils/qr.js`（约 9 KB），我的模块页面约 20 KB，远低于主包预算；无需分包 |
| 最低基础库 | 原型无基础库概念。若迁移：`Array.from`、`String.prototype.padStart`、`canvas.toBlob` 需基础库 2.x；二维码编码器为纯 JS，无 API 依赖 |
| 后台配置 | 无域名、无支付、无订阅消息；推荐码链接域名 `pay.hifox.demo` 仅作演示，不请求网络。真实拉新需在公众平台配置业务域名并改为正式链接 |
| 审核 | 原型不提交审核。若上小程序：头像需相册/相机授权与内容安全检测；手机号修改属个人信息变更，需隐私协议声明；推荐码分享不得诱导分享 |

## 6. 取舍

| 方案 | 取舍 |
|---|---|
| 个人资料独立页 vs 全部用抽屉 | 选独立页：字段多、有保存与审核态，抽屉会过深；其余 5 项用抽屉，保持「我的」页层级浅 |
| 真实二维码 vs 沿用伪码 | 选真实编码器：验收要求「二维码含编号」，伪码无法回读；代价是 `mobile.js` 增加约 9 KB |
| 卡号 Luhn 校验 | 未启用：常见测试卡号多不满足 Luhn，会在验收时误伤；改为「数字 + 16–19 位 + 首位 4–6」，真实鉴权留给服务端 |
| 修改立即生效 vs 一律审核 | 除头像外全部进「审核中」：符合设计规范「修改手机号需审核」「结算卡变更需审核」，也避免演示数据被误认为已生效 |

## 7. 遗留与风险

1. **空态**：按设计规范标 N/A，仅演示切换器保留占位；如果验收要求「六个可点击状态」，需要产品确认空态的业务含义。
2. **审核结果无回写**：昵称/手机号/结算卡提交后停在「审核中」，没有演示「审核通过」入口；后台审核流不在本次范围。
3. **二维码内容为演示域名**：`https://pay.hifox.demo/i/<编号>` 不解析、不请求；接入真实拉新时替换为正式短链，并同步隐私与分享口径。
4. **卡号校验仅前端格式**：不校验 Luhn/银行四要素；真实环境必须服务端鉴权，前端不持有完整卡号。
5. **我的钱包无独立页**：按裁决保留「跳收益页」，MP-121 仍按「入口已实现」验收。
6. **未修的相邻缺陷**：门店卡片行、码牌商户选择器（B-NAV-06 / V2-BUG-03）不在本次范围，已在审计文档列出。
